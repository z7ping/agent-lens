# AgentLens 产品长期方向

更新日期：2026-08-21

## 这份文档解决什么问题

这不是版本 Roadmap，也不承诺具体发布时间。

它只回答三个长期问题：

1. AgentLens 最终想成为什么；
2. 哪些能力值得持续投入；
3. 哪些方向明确不作为主要目标。

具体版本范围、实现状态和技术约束，分别由版本文档、`IMPLEMENTATION-STATUS.md`、`CORE-CONTRACT.md` 与 ADR 承担。

---

## 长期产品定位

AgentLens 起点是本地 AI Agent 的执行轨迹观测：看清不同 Agent 装了什么、用了什么、一次任务是怎么完成的。

长期目标不只是“日志查看器”或“轨迹查看器”，而是逐步成为：

> **个人 AI 工作环境的观测、资产管理与理解中心。**

这个定位包含三个核心动词：

- **看清**：知道 Agent 在做什么、调用了什么、哪里失败了；
- **保住**：知道自己的 Skill、配置、规则、Session 等资产在哪里，并能安全保存；
- **看懂**：基于真实使用事实理解自己的 AI 工具、能力与工作流是如何被使用的。

---

## 长期主线一：可靠观测

这是 AgentLens 的基础能力，也是其他能力成立的前提。

长期要求：

- 对不同 Agent 的 Session、Interaction、Tool Call、Asset Usage 保持可追溯；
- 区分“发现 / 安装 / 配置”和“真实使用”；
- 尽可能保留原始 Evidence，避免只留下二次推导结果；
- 同一原生事件被多个入口观察到时仍保持事实去重；
- 新的分析能力不得绕开事实层直接制造结论。

当前优先支持 Codex、Claude Code、Pi。后续是否接入其他 Agent，按真实价值决定，而不是追求支持数量。

---

## 长期主线二：AI 资产管理

AgentLens 已经具备 Asset Inventory，后续在此基础上继续扩展“资产保存与迁移”能力。

重点资产包括：

- Skill；
- Rule / Memory；
- Session / History；
- MCP 配置；
- Plugin / Extension 配置；
- Hook 配置；
- Agent 本身的重要配置。

长期演进方向：

```text
资产发现
  ↓
资产清单
  ↓
本地备份
  ↓
版本快照
  ↓
恢复
  ↓
迁移
```

第一阶段只关注本地可靠备份与完整性校验，不默认备份 API Key、Token、Credential 等敏感信息。

备份应优先保存原始资产与原始 Session 数据，而不是把 AgentLens 的 Projection 或分析结果当作唯一备份内容。

云同步、Git 同步、WebDAV、NAS、自动跨设备迁移、增量备份等能力可以后续评估，不作为当前基础能力的前置条件。

---

## 长期主线三：AI 使用分析与洞察

AgentLens 的分析必须建立在可靠事实之上，而不是先构造评分体系。

从产品能力上，分析应逐步从“统计”走向“模式”和“洞察”：

```text
事实
 ↓
统计
 ↓
模式
 ↓
洞察
```

未来可以回答的问题包括：

- 哪些 Skill / MCP 装了但长期没有实际使用；
- 哪些 Tool / Skill / MCP 使用最频繁；
- 哪些 Agent 在什么类型任务中更常被使用；
- 哪类任务更容易失败；
- 哪些工具经常组合出现；
- 某个 Skill 是否真正进入了日常工作流；
- 用户的 AI 工作流如何随时间演进。

这些能力必须能够追溯到底层 Observation / Evidence，避免把启发式猜测包装成事实。

---

## 长期主线四：有限而可扩展的 Source / Plugin 生态

AgentLens 不以“接入所有 Agent”为目标。

核心仓库只维护少数高价值、质量可控的 Source。其他 Agent 可以逐步通过插件方式扩展。

选择是否接入一个新 Source，优先看：

- 是否有真实使用价值；
- 是否能稳定取得可验证数据；
- 是否值得长期维护；
- 是否能复用现有 Contract，而不是迫使 Core 出现按 Source 特判。

候选方向可以包括 OpenCode、Hermes、OpenClaw、Cursor 等，但不在本文承诺具体接入顺序。

---

## 1.0 当前阶段目标

1.0 的目标不是继续扩张功能，而是把基础能力真正收口：

- 完成真实 UI 使用体验验收；
- 核对 Codex / Claude Code / Pi 的真实本机数据；
- 完成 Windows 安装、启动、托盘、退出、卸载等真实体验验证；
- 验证长时间运行与异常恢复；
- 确认安装后首次启动体验；
- 在此基础上决定 1.0 的最终发布边界。

新的长期能力可以先记录，但不应打断 1.0 的收口节奏。

---

## 明确不作为主要目标的方向

### 不做通用 AI Agent 平台

AgentLens 不负责执行用户任务，也不试图替代 Claude Code、Codex、Pi 或其他 Harness / Agent Runtime。

### 不追求支持所有 Agent

支持数量不是核心指标。质量、可观测性和长期维护价值优先。

### 不把推测包装成事实

价值分、风险分、推荐工作流等启发式能力只有在重新设计、可解释并能追溯 Evidence 时才考虑引入。

### 不为新功能破坏事实层

备份、恢复、洞察、插件等能力都应建立在稳定 Contract 之上，不应绕过 Canonical Observation / Evidence 体系制造第二套事实来源。

### 不过早建设重型同步系统

在本地资产备份没有验证价值之前，不优先投入云端账户、同步服务、多设备中心、远程存储等基础设施。

---

## 用一句话判断一个新需求是否值得做

当出现新的功能想法时，优先判断它是否帮助用户做到以下至少一件事：

> **更清楚地看见自己的 AI 在做什么，更可靠地保存自己的 AI 资产，或者更准确地理解自己的 AI 使用方式。**

如果一个需求与这三件事都无关，它默认不是 AgentLens 的优先方向。
